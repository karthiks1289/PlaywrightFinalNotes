Memory hook: Browser → Context → Page.

A context is like a separate browser session. Logging in within Context 1 does not automatically log in Context 2.

2. Why use BrowserContext?

  • Test multiple users independently.
  • Prevent one test's login state from affecting another.
  • Test roles such as Admin and Customer.
  • Handle multiple tabs and popups.
  • Reuse supported authentication state when needed.

4. Creating contexts and pages

Multiple pages in one context

const context = await browser.newContext();

const page1 = await context.newPage();
const page2 = await context.newPage();
const page3 = await context.newPage();

Separate contexts

const context1 = await browser.newContext();
const context2 = await browser.newContext();

const page1 = await context1.newPage();
const page2 = await context2.newPage();

Pages in one context share context-level browser storage where the browser's storage rules allow it. Different contexts are isolated.

5. Popup, new tab and same-tab navigation

Expected behaviourUse
Current page opens a popup/new tabpage.waitForEvent("popup")
A new page appears anywhere in this contextcontext.waitForEvent("page")
Current tab navigates to another URLpage.waitForURL()

A. Capture a popup opened by the current page

const [popup] = await Promise.all([
  page.waitForEvent("popup"),
  page.getByRole("link", { name: "Open Report" }).click()
]);

console.log(popup.url());

Listener is registered before the click action is triggered. Promise.all() waits for both promises.

B. Capture a new page anywhere in the context

const [newPage] = await Promise.all([
  context.waitForEvent("page"),
  page.getByRole("button", { name: "Open Window" }).click()
]);

context.waitForEvent("page") waits for one new-page event. For repeated events, use context.on("page", ...).

C. Register promise separately

const popupPromise = page.waitForEvent("popup");

await page.getByRole("link", { name: "Open Report" }).click();

const popup = await popupPromise;

D. Nested popups

const reportPromise = page.waitForEvent("popup");
await page.getByRole("link", { name: "Open Report" }).click();
const reportPage = await reportPromise;

const detailsPromise = reportPage.waitForEvent("popup");
await reportPage.getByRole("link", { name: "Open Details" }).click();
const detailsPage = await detailsPromise;

Memory hook: Listen on the page that triggers the popup.

E. Capture multiple pages

const newPages: Page[] = [];

context.on("page", newPage => {
  newPages.push(newPage);
});

await page.getByRole("button", { name: "Open Reports" }).click();

await expect.poll(() => newPages.length).toBe(3);

for (const newPage of newPages) {
  console.log(newPage.url());
  console.log(await newPage.title());
}

Use a deterministic application condition and an appropriate timeout when waiting for a known number of pages.

6. Race condition

Incorrect – listener registered too late 
await page.getByRole("link", { name: "Report" }).click();
const popup = await page.waitForEvent("popup");
The popup might open before the listener starts. The event can be missed.
Correct – listener before action 
const [popup] = await Promise.all([
  page.waitForEvent("popup"),
  page.getByRole("link", { name: "Report" }).click()
]);
Memory hook: Listener first → Action second → Wait for completion.

7. Same-tab navigation

await Promise.all([
  page.waitForURL("**/dashboard"),
  page.getByRole("link", { name: "Dashboard" }).click()
]);

// Alternative retrying assertion:
await expect(page).toHaveURL(/dashboard/);

waitForURL() waits for URL matching. expect(page).toHaveURL() is a retrying assertion. Neither alone guarantees that the required business UI is ready.

8. Page load vs element readiness

Wait for a page load milestone

await popup.waitForLoadState("load");
StateMeaning
commitNavigation response received and document committed
domcontentloadedHTML parsed and DOMContentLoaded fired
loadPage load event fired after dependent resources load

Wait for the required UI element (often preferred)

await expect(
  popup.getByRole("heading", { name: "Order Details" })
).toBeVisible({ timeout: 15000 });
Important: locator.isVisible() checks current visibility; it does not auto-wait. expect(locator).toBeVisible() retries until visible or timeout. A page's load event does not mean all API data is ready.

Avoid fixed waits such as page.waitForTimeout(5000) as a default. Prefer condition-based waits.

9. Find one or multiple pages

Find one page using URL

const pages = context.pages();

const reportPage = pages.find(page =>
  page.url().includes("/report")
);

if (reportPage && !reportPage.isClosed()) {
  console.log(await reportPage.title());
}

Find multiple pages using a synchronous condition

const reportPages = context.pages().filter(page =>
  page.url().includes("/report")
);

Find pages using asynchronous titles

for (const page of context.pages()) {
  const title = await page.title();

  if (title.includes("Report")) {
    console.log(title);
    await page.close();
  }
}
ApproachUse
find()First matching item
filter()All matching items with a synchronous condition
for...ofProcess pages with await
Avoid: 
pages.find(async page =>
  (await page.title()).includes("Report")
);
find() does not wait for asynchronous callbacks.

10. Close pages safely

Close one page

await page.close();

Find and close one page by URL

const openCartPage = context.pages().find(page =>
  page.url().includes("/opencart/")
);

if (openCartPage && !openCartPage.isClosed()) {
  await openCartPage.close();
}

Close all pages whose title matches

for (const page of context.pages()) {
  const title = await page.title();

  if (title.includes("Report")) {
    await page.close();
  }
}
MethodScope
page.close()One page
context.close()All pages in that context
browser.close()Browser and all its contexts

11. Detect popup closure

// Listen for a future close event
popup.on("close", () => {
  console.log("Popup closed");
});

// Check current state before interacting
if (!popup.isClosed()) {
  await popup.getByRole("button", { name: "Submit" }).click();
}

on("close") listens for a future event. isClosed() checks current state. Register listeners as early as possible.

12. Storage sharing and authentication

StorageShared across pages in same context?
CookiesYes, subject to cookie scope/rules
localStorageYes, for the same origin
sessionStorageGenerally separate per tab/top-level browsing context

Reuse supported authentication state across contexts

await context1.storageState({ path: "auth.json" });

const context2 = await browser.newContext({
  storageState: "auth.json"
});
Important: Storage state supports cookies and localStorage (and supported authentication state); it does not automatically save sessionStorage. SessionStorage behaviour may require a separate setup if the application depends on it.

13. Cleanup with try/finally

test("Context cleanup", async ({ browser }) => {
  const context = await browser.newContext();

  try {
    const page1 = await context.newPage();
    const page2 = await context.newPage();

    await page1.goto("https://example.com");

    // Test execution
  } finally {
    await context.close();
  }
});

finally runs whether the try block succeeds or throws. Close the resource you created. Playwright Test manages built-in fixtures such as { page }, { context } and { browser }; do not close a shared fixture unnecessarily.

14. JavaScript async concepts used here

Promise.all()

const [popup] = await Promise.all([
  page.waitForEvent("popup"),
  page.getByRole("link", { name: "Report" }).click()
]);

Starts the supplied promise operations and waits for all to fulfill. If one rejects, the combined Promise rejects; it does not automatically cancel the other operation.

forEach(async...) – common mistake

pages.forEach(async page => {
  console.log(await page.title());
});
forEach() does not wait for async callbacks.

Sequential processing

for (const page of pages) {
  console.log(await page.title());
}

Parallel processing

await Promise.all(
  pages.map(async page => {
    console.log(await page.title());
  })
);
RequirementUse
One after anotherfor...of
ConcurrentlyPromise.all(array.map(...))
First matching itemfind()
All matching itemsfilter()

15. URL matching patterns

// Exact URL
await page.waitForURL("https://example.com/dashboard");

// Glob pattern
await page.waitForURL("**/dashboard");

// Regular expression
await page.waitForURL(/dashboard/);

// Function
await page.waitForURL(url =>
  url.pathname.includes("dashboard")
);

For redirects, generally wait for the final expected URL. URL matching alone does not prove the business UI is ready.

17. Common mistakes – last-minute revision

  • Registering popup listener after click → can miss event.
  • Using popup event for same-tab navigation → use waitForURL().
  • Using page popup listener for unrelated pages → consider context page event.
  • Using find(async...) → callback is not awaited.
  • Using forEach(async...) → outer code does not wait.
  • Assuming page load means UI is ready → assert the required element.
  • Using isVisible() as an auto-wait → use expect().toBeVisible().
  • Closing browser when only one context should close → use context.close().
  • Assuming sessionStorage is shared → generally separate per tab.
  • Using fixed waits everywhere → prefer condition-based waits.

19. Practical assignments – real-time implementation & interview preparation

Complete these in order. Build them in your own Playwright + TypeScript project. Use the Playwright Test runner, meaningful test names, reliable locators, assertions, and proper cleanup. Do not copy a solution first: implement, run, debug, and then review.

How to practise each assignment
1. Read the requirement and write the test yourself.
2. Run it at least twice to check reliability.
3. Intentionally introduce one failure and observe the error.
4. Remove fixed waits and use event-based or condition-based waiting.
5. Explain why your approach works, as if answering a Senior SDET interviewer.

Level 1 – Core browser and context skills

Assignment 1 – Two isolated user sessions

Scenario: An application supports Admin and Standard User accounts. Verify that their browser sessions are independent.

  • Create two BrowserContexts from one Browser.
  • Open the same application in both contexts.
  • Log in as Admin in Context 1 and as Standard User in Context 2.
  • Verify the correct user identity or role in each page.
  • Verify that logging out in Context 1 does not log out Context 2.

Acceptance criteria: Two contexts are created; each has its own login state; the test proves isolation with assertions.

Skills: browser.newContext(), context.newPage(), cookies, authentication, assertions.

Assignment 2 – Multiple tabs in one context

Scenario: An agent works with a customer record and an order record in separate tabs.

  • Create one context and open three pages.
  • Navigate each page to a different application route.
  • Use context.pages() to retrieve all open pages.
  • Assert that exactly three pages are open.
  • Identify the customer page by URL and verify a customer-specific heading.

Acceptance criteria: Do not depend on page array indexes to identify the customer page.

Skills: context.pages(), page.url(), find(), locator assertions.

Assignment 3 – Close only the matching page

Scenario: A workflow opens several tabs, but a report tab must be closed while the others remain available.

  • Open at least four pages in one context.
  • Identify the page whose URL contains a chosen route such as /report.
  • Close only that page.
  • Assert that the other pages remain open and the page count decreases by one.
  • Handle the case where no matching page exists.

Acceptance criteria: No broad context.close() or browser.close() is used to close one tab.

Skills: find(), isClosed(), page.close(), page-count assertions.

Level 2 – Popup, navigation and event handling

Assignment 4 – Capture a popup and validate its content

Scenario: Clicking “Open Invoice” launches an invoice in a new tab.

  • Register the popup listener before clicking.
  • Capture the popup using page.waitForEvent("popup").
  • Wait for the expected invoice URL.
  • Assert the invoice heading, invoice number, and one key detail.
  • Take a screenshot of the popup if the assertion fails (optional enhancement).

Acceptance criteria: No race condition; validate both navigation and business content.

Skills: waitForEvent("popup"), Promise.all(), waitForURL(), expect().

Assignment 5 – Same-tab navigation (not a popup)

Scenario: Clicking “Dashboard” navigates the current tab to the dashboard route.

  • Wait for the expected URL while clicking the link.
  • Assert that the current page URL matches the dashboard.
  • Assert that the dashboard heading or main landmark is visible.
  • Explain why waiting for a popup would be incorrect.

Acceptance criteria: Use the existing Page object; do not expect a new Page to be created.

Skills: page.waitForURL(), toHaveURL(), locator readiness.

Assignment 6 – Capture a page created anywhere in the context

Scenario: A toolbar action opens a new page, but the page that triggers it may vary.

  • Register context.waitForEvent("page") before the action.
  • Trigger the action from a page.
  • Assert the new page's expected URL and title or heading.
  • Explain when this context-level event is more suitable than a page-level popup event.

Acceptance criteria: Correct event scope; listener registered before action.

Skills: context.waitForEvent("page"), event ordering, URL/title checks.

Assignment 7 – Multiple popups from one action

Scenario: Clicking “Open batch reports” opens three report pages.

  • Register context.on("page", ...) before clicking.
  • Collect the new Page objects in an array.
  • Wait for the expected number of pages using a condition-based wait.
  • Validate each page by URL or heading.
  • Close only the pages created by this action.

Acceptance criteria: Capture all expected pages, not just the first event. Avoid arbitrary sleeps.

Skills: context.on("page"), arrays, expect.poll(), cleanup.

Level 3 – Readiness, storage and robust automation

Assignment 8 – Popup loads slowly

Scenario: The popup appears quickly, but its content loads after an API response.

  • Capture the popup.
  • Wait for a meaningful business element, not just the page load event.
  • Use a retrying assertion with a sensible timeout.
  • Explain the difference between load and application readiness.
  • Do not use waitForTimeout() as the solution.

Acceptance criteria: The test waits for the actual element required by the next action.

Skills: waitForLoadState(), expect().toBeVisible(), timeouts, dynamic UI.

Assignment 9 – Authentication state reuse

Scenario: A login flow is expensive, and later tests need to start already authenticated.

  • Log in using a setup step or setup test.
  • Save state using context.storageState({ path: "auth.json" }).
  • Create a fresh context using that storage state.
  • Verify that the new context is authenticated.
  • Document whether the application relies on cookies, localStorage, or sessionStorage.

Acceptance criteria: Demonstrate reuse in a separate context; do not claim storageState automatically persists sessionStorage.

Skills: storageState(), context isolation, authentication setup.

Assignment 10 – Popup closes unexpectedly

Scenario: A popup may close after a user action or application response.

  • Register a close listener as soon as you have the popup reference.
  • Record that the close event occurred.
  • Before a later action, check isClosed().
  • Handle the closed-page path without trying to interact with a closed page.

Acceptance criteria: Distinguish between listening for a future close and checking current state.

Skills: page.on("close"), page.isClosed(), defensive checks.

Assignment 11 – Reliable cleanup after failure

Scenario: A test creates a manual context and fails halfway through.

  • Create a context and at least two pages inside a try block.
  • Force an assertion failure temporarily.
  • Use finally to close the manually created context.
  • Run the test and verify cleanup still happens after failure.
  • Explain why you should not close a Playwright Test fixture browser unnecessarily.

Acceptance criteria: Cleanup runs on both pass and fail paths; only the owned context is closed.

Skills: try/finally, fixture lifecycle, context cleanup.

Level 4 – Senior SDET interview challenges

Assignment 12 – Build a reusable popup helper

Scenario: Several tests need to click a control and capture the popup it opens.

  • Create a reusable TypeScript helper that accepts the parent Page and a click action or locator.
  • Register the popup event before triggering the action.
  • Return the captured Page to the test.
  • Use the helper in at least two tests.
  • Keep the helper typed and avoid using any.

Acceptance criteria: Reusable, readable helper; event listener is never registered after the action.

Skills: TypeScript types, async functions, Promise, reusable test utilities.

Assignment 13 – Identify pages by business meaning, not array position

Scenario: A workflow opens a customer page, an order page and a report page in an unpredictable order.

  • Open all three pages.
  • Identify each page using a stable URL fragment or page-specific heading.
  • Do not assume context.pages()[0] is always the customer page.
  • Handle a missing page explicitly and produce a useful failure message.

Acceptance criteria: Reliable identification even if opening order changes.

Skills: Page collections, URL matching, async title checks, defensive assertions.

Assignment 14 – Diagnose a flaky multi-window test

Scenario: A test passes locally but intermittently times out in CI while waiting for a popup or heading.

  • Review event registration order.
  • Check whether the action opens a popup or navigates the same page.
  • Check whether the popup is created but navigates later.
  • Check whether the expected element is delayed, missing, or incorrectly located.
  • Replace fixed waits with the correct event and condition-based assertion.
  • Add useful logs such as page URL and title when diagnosing.

Acceptance criteria: Explain the root cause and fix, not just increase every timeout.

Skills: Debugging, race conditions, navigation lifecycle, CI reliability.

Assignment 15 – End-to-end multi-window workflow

Scenario: An operations user logs in, opens an order, opens an invoice popup, verifies invoice data, opens a report in another tab, then closes the report and logs out.

  1. Create the appropriate context and page.
  2. Log in and assert the authenticated user.
  3. Open the order and assert its details.
  4. Capture the invoice popup and wait for the invoice content.
  5. Open the report page and identify it by URL or title.
  6. Close only the report page and verify the order and invoice pages remain open.
  7. Log out and clean up the context in finally.

Acceptance criteria: The complete flow is stable, uses no arbitrary fixed waits, has meaningful assertions, and cleans up correctly even on failure.

Skills: Integration of the full module; realistic multi-window workflow; test design.

What should you be able to do before the interview?

  • Write the popup and same-tab navigation patterns without notes.
