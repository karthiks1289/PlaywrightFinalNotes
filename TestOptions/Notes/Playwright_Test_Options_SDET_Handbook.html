Playwright Test Options

End-to-end training handbook: what each option controls, where it belongs, when to use it, practical examples, common mistakes, interview questions and assignments.

Accuracy note
These notes are checked against the official Playwright documentation available on 13 November 2026. Some options are version-dependent. Check your installed Playwright version before using newer properties. Examples use @playwright/test with TypeScript.

1. The mental map

Imagine a Salesforce automation suite with hundreds of tests. You need to control test selection, execution speed, browser conditions, time limits, and failure evidence.

Discover tests → Configure run → Create browser context → Run tests → Report evidence
TestConfigGlobal test-runner settings in playwright.config.ts.
TestProjectA named execution configuration, e.g. Chromium or Firefox.
TestOptions / useBrowser and browser-context environment for tests.
Test APIMethods used in test files, e.g. test.skip() and test.step().
CLI optionsOne-run overrides, e.g. --workers=1.
Fixtures and hooksProvide test resources and setup/cleanup.
Do not mix these categories. retries is a test-runner configuration property. test.skip() is a test API annotation. --retries=2 is a command-line option. They are related, but not the same type of thing.

2. Where configuration belongs

ScopeWhereWhat it controls
Globalplaywright.config.tsDefaults for the complete test run.
Projectprojects: [{ ... }]One browser, device, environment or test group configuration.
File / describe grouptest.use(), test.describe.configure()Supported fixture/options or execution mode for that scope.
Individual testTest details, modifiers, test.setTimeout()One test's metadata, behaviour or timeout.
One commandCLI flagsTemporary override for that invocation.

Memory hook: Global → Project → Group/File → Individual test. The exact override rules depend on the option; not every setting is overridable at every scope.

3. Test-runner configuration options (TestConfig)

3.1 Test discovery

OptionMeaningExample / use
testDirDirectory where Playwright searches for test files.testDir: './tests'
testMatchFile patterns considered test files.testMatch: '**/*.spec.ts'
testIgnoreFile patterns excluded from discovery.testIgnore: '**/legacy/**'
grepRun tests whose title/annotations match a regular expression.grep: /@smoke/
grepInvertExclude tests matching a regular expression.grepInvert: /@slow/
respectGitIgnoreControls whether discovery respects .gitignore. Version-sensitive; documented as added in v1.45.Check installed version and current docs.

3.2 Execution, parallelism and retries

OptionMeaningImportant detail
workersMaximum number of concurrent worker processes.Each worker is an OS process and launches its own browser. More workers consume more CPU/memory.
fullyParallelAllows tests within files to run in parallel across workers.Default behaviour: files can run in parallel; tests in one file run in order in one worker.
retriesMaximum additional attempts for a failed test.Default is 0. A pass after an initial failure is classified as flaky.
retryStrategyControls when retries are scheduled.Current docs: immediate (default) or isolated. Added in v1.62; verify version.
repeatEachRepeats each selected test the configured number of times.Unlike retries, it repeats tests even when they pass.
maxFailuresStops the run after the specified number of test failures.0 means no configured failure limit.
globalTimeoutMaximum duration for the entire test run.Default 0 (no global limit).
forbidOnlyFails the run if focused tests/groups are present.Common CI protection: forbidOnly: !!process.env.CI.
failOnFlakyTestsCan make the run fail if tests are classified as flaky.Useful for enforcing CI quality; check installed version.
export default defineConfig({
  workers: process.env.CI ? 2 : undefined,
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  forbidOnly: !!process.env.CI,
  maxFailures: process.env.CI ? 10 : 0
});
Workers vs fullyParallel
Workers = how many worker processes may run concurrently. fullyParallel = whether individual tests within a file are eligible to run in parallel too. Neither setting makes dependent tests safe. Keep tests independent.
Retries vs repeatEach
Retries only re-run failed tests. repeatEach repeats every selected test the specified number of times, including tests that passed.

3.3 Projects and sharding

projects lets the same test suite run under different configurations: browser engines, branded browsers, devices, environments, or setup/teardown workflows.

projects: [
  { name: 'chromium', use: { browserName: 'chromium' } },
  { name: 'firefox',  use: { browserName: 'firefox' } },
  { name: 'webkit',   use: { browserName: 'webkit' } }
]

Sharding splits a test suite across separate CI jobs/machines. Example CLI: npx playwright test --shard=1/3. Run the other shards as --shard=2/3 and --shard=3/3. Workers are parallelism inside a run; shards distribute work across runs/jobs.

3.4 Reports and output

OptionMeaning
reporterReporter(s), e.g. list, line, dot, html, json, junit, github, blob.
outputDirDirectory for test output and attachments, commonly ./test-results.

reportSlowTestsConfigures reporting of slow tests.
preserveOutputControls when test output directories are cleaned/preserved.

reporter: [
  ['list'],

outputDir: './test-results'

3.5 Setup, teardown and local server

OptionMeaning
globalSetupRuns setup code before the test run.
globalTeardownRuns cleanup code after the test run.
webServerStarts a local server and waits for its URL to become available.
Project dependenciesRuns prerequisite projects before dependent projects.
Project teardownAssociates a teardown project with a setup project.
webServer: {
  command: 'npm run start',
  url: 'http://localhost:3000',
  reuseExistingServer: !process.env.CI
}

For setup that should appear in Playwright's project/report lifecycle, consider a setup project with project dependencies. Use global setup/teardown when the work is truly global and does not need to be represented as a test project.

4. Browser and context options (the use object)

These options configure the browser launch or the BrowserContext used by Playwright Test. The exact underlying destination matters: some settings are launch options; many are context settings.

4.1 Browser selection and launch

OptionMeaning
browserNameBrowser engine: chromium, firefox or webkit. Test runner default is chromium.
channelBranded browser channel, e.g. Chrome or Edge where supported.
headlessWhether browser UI is hidden. Default true in standard Playwright Test configuration.
launchOptionsOptions passed to browserType.launch(), such as supported launch flags/settings.
connectOptionsOptions for connecting to a browser server, when using a remote connection.
contextOptionsBrowserContext creation options grouped under this property.

Do not confuse browserName: 'chromium' (engine) with channel: 'chrome' (branded distribution).

4.2 Viewport and device emulation

OptionMeaning
viewportPage viewport width and height.
screenEmulated screen dimensions; used with device emulation settings.
deviceScaleFactorDevice pixel ratio.
isMobileEnables mobile browser emulation behaviour where supported.
hasTouchEnables touch support.
userAgentOverrides browser user-agent string.
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [{
    name: 'mobile-chromium',
    use: { ...devices['Pixel 7'] }
  }]
});

Device emulation is not the same as testing on a physical phone. It emulates browser/device characteristics.

4.3 URL and authentication

OptionMeaning
baseURLBase URL used to resolve relative navigation such as page.goto('/accounts').
storageStateLoads saved cookies and supported browser storage into a context; commonly used for authenticated tests.
use: {
  baseURL: process.env.BASE_URL,
  storageState: 'playwright/.auth/user.json'
}
Security: Authentication state files can contain credentials/session tokens. Keep them out of public repositories and protect them in CI. Storage state is not a complete copy of every browser storage mechanism; sessionStorage needs separate handling.

4.4 Locale, time and permissions

OptionMeaning
localeBrowser locale and regional formatting preferences.
timezoneIdBrowser timezone.
geolocationSimulated latitude/longitude.
permissionsGrant browser permissions, e.g. geolocation or notifications where supported.
colorSchemeEmulates light/dark preference.
reducedMotionEmulates reduced-motion preference.
forcedColorsEmulates forced-colours preference.
use: {
  locale: 'en-GB',
  timezoneId: 'Europe/London',
  colorScheme: 'dark',
  geolocation: { latitude: 51.5072, longitude: -0.1276 },
  permissions: ['geolocation']
}

4.5 Network, security and service workers

OptionMeaning / caution
offlineEmulates offline network state.
proxyConfigures a proxy for browser traffic.
extraHTTPHeadersAdditional HTTP headers sent with requests.
httpCredentialsHTTP authentication credentials (not the same as app login).
ignoreHTTPSErrorsIgnores HTTPS certificate errors; use only when the test environment requires it.
clientCertificatesConfigures client certificates for mutual TLS scenarios.
serviceWorkersControls service-worker handling, e.g. allow or block.
bypassCSPBypasses Content Security Policy; generally not a normal production-like test setting.

4.6 Downloads, dialogs and test IDs

OptionMeaning
acceptDownloadsWhether downloads are accepted automatically. Current API docs list default true.
testIdAttributeChanges the attribute used by getByTestId(); default is data-testid.
javaScriptEnabledEnables/disables JavaScript in the context; default true.
httpCredentialsSets HTTP authentication credentials.

4.7 Screenshot, video and trace

SettingCommon valuesMeaning
screenshotoff, on, only-on-failureAutomatic screenshot capture.
videooff, on, retain-on-failure, on-first-retryVideo recording and retention policy.
traceoff, on, retain-on-failure, on-first-retry, retain-on-first-failureDetailed execution trace and retention policy.

Practical CI choice: screenshot: 'only-on-failure', video: 'retain-on-failure', trace: 'on-first-retry'. This is a starting point, not a universal rule. Trace Viewer can show actions, snapshots, network activity and timing information.

5. Test API methods and modifiers

MethodWhat it doesRemember
test.skip()Marks a test as irrelevant/not to be run.Conditional skip is useful for browser-specific limitations.
test.only()Focuses execution on selected tests.Protect CI with forbidOnly.
test.fail()Runs the test but expects it to fail.If it passes, Playwright reports an unexpected pass/failure.
test.fixme()Marks test for fixing and does not run it.Use for known broken/unfinished tests.
test.slow()Triples the test timeout.Does not slow the test down; increases its allowed time.
test.describe()Groups tests and scopes hooks/configuration.Think of a logical test suite/module.
test.describe.configure()Sets group execution mode: default, parallel or serial.Serial mode has failure/skip implications; prefer independent tests.
test.use()Overrides supported fixtures/options for a file or describe scope.Not a way to change browser options halfway through a running test.
test.setTimeout()Changes timeout for a test or relevant hook scope.Use milliseconds.
test.step()Creates named steps in the report.Improves readability and failure diagnosis.
test.info()Provides information about the currently running test.Can access attachments, annotations, status and test metadata.
test.describe('Salesforce Account tests', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/accounts');
  });

  test('Create account @smoke', async ({ page }) => {
    await test.step('Open new account form', async () => {
      await page.getByRole('button', { name: 'New' }).click();
    });

    await test.step('Verify form is visible', async () => {
      await expect(page.getByRole('heading', { name: 'New Account' }))
        .toBeVisible();
    });
  });
});

Execution modes: default is the normal mode; parallel runs tests in the group in separate worker processes; serial runs in order and subsequent tests are skipped if a test in the serial group fails. Serial mode is generally discouraged because it creates dependencies between tests.

6. Timeout options — do not confuse them

TimeoutControlsDefaultConfigured at
Test timeoutTest function, fixture setup and beforeEach time.30,000 mstimeout
Expect timeoutAuto-retrying assertion wait.5,000 msexpect.timeout or assertion option
Action timeoutIndividual action such as click/fill.0 (no limit)use.actionTimeout
Navigation timeoutNavigation actions.0 (no limit)use.navigationTimeout
Global timeoutWhole test run.0 (no limit)globalTimeout
Hook timeoutbeforeAll/afterAll hooks.Defaults to test timeouttest.setTimeout() / testInfo timeout in hook
Subtle but important: The test timeout includes the test function, fixture setup and beforeEach. Fixture teardown and afterEach have a separate timeout budget of the same value. beforeAll/afterAll have their own timeout budget. Assertion timeout is separate from test timeout.
export default defineConfig({
  timeout: 60_000,
  expect: { timeout: 10_000 },
  use: {
    actionTimeout: 15_000,
    navigationTimeout: 20_000
  },
  globalTimeout: 3_600_000
});

For one test: test.setTimeout(60_000). For one assertion: await expect(locator).toBeVisible({ timeout: 10_000 }). For one action: await locator.click({ timeout: 8_000 }).

7. Tags and annotations

Tags classify tests; annotations attach additional information. Tags must start with @.

test('Create account', {
  tag: ['@smoke', '@regression'],
  annotation: {
    type: 'requirement',
    description: 'CRM-101'
  }
}, async ({ page }) => {
  // test steps
});
npx playwright test --grep "@smoke"
npx playwright test --grep-invert "@slow"
npx playwright test --grep "@smoke|@regression"

Use regex lookaheads if you need tests carrying both tags: --grep "(?=.*@smoke)(?=.*@regression)".

8. Hooks and lifecycle

HookWhenTypical use
test.beforeAll()Before tests in its scope in a worker.Worker-level preparation.
test.beforeEach()Before each test.Navigate to page, create per-test setup.
test.afterEach()After each test.Per-test cleanup.
test.afterAll()After tests in its scope in a worker.Worker-level cleanup.

Important: beforeAll/afterAll are not guaranteed to run just once for the entire CI pipeline. Parallel workers have their own execution scopes. Tests should normally be isolated and independently set up.

10. A practical starter configuration

This is a learning template, not a one-size-fits-all production configuration. Set BASE_URL in your environment. Start with fewer workers in CI if the agent has limited resources.

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  testMatch: '**/*.spec.ts',

  timeout: 30_000,
  expect: { timeout: 5_000 },

  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,
  fullyParallel: true,
  forbidOnly: !!process.env.CI,

  reporter: [
    ['list'],
    ['html', { open: 'never' }]
  ],
  outputDir: './test-results',

  use: {
    baseURL: process.env.BASE_URL,
    headless: !!process.env.CI,
    actionTimeout: 10_000,
    navigationTimeout: 20_000,
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'on-first-retry'
  },

  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } }
  ]
});
Configuration note: Project-level use values can override corresponding top-level use values. In the example, device descriptors may provide their own viewport/device settings. Review the resolved project configuration rather than assuming every global setting wins.

11. Common mistakes to avoid

  1. Putting runner settings such as retries or workers inside use. They belong at the test-config/project level, not in browser context options.
  2. Leaving test.only() in a shared branch. Enable forbidOnly in CI.
  3. Increasing timeouts to hide poor synchronization. Prefer Playwright auto-waiting and reliable locators.
  4. Increasing workers without checking CPU, memory, test data collisions and environment capacity.
  5. Using retries to hide product defects or unstable tests instead of investigating root causes.
  6. Making tests depend on the order of other tests. Prefer independent setup and cleanup.
  7. Assuming storageState saves every kind of browser storage. Session storage needs separate handling.
  8. Confusing browser engine (browserName) with branded browser channel (channel).
  9. Assuming test.slow() slows the test. It triples the timeout.
  10. Assuming a worker is a browser tab. A worker is an operating-system process; it launches its own browser.

12. Interview questions with short answers

1. What is the difference between TestConfig and TestOptions?
TestConfig controls test discovery and the test run. TestOptions configure the browser/browser-context environment used by tests, usually under use.
2. What is the difference between workers and fullyParallel?
Workers set the maximum concurrent worker processes. fullyParallel allows tests within a file to run in parallel too.
3. What is the difference between retries and repeatEach?
Retries re-run failed tests. repeatEach repeats every selected test, whether it passes or fails.
4. What is a flaky test?
A test that fails on its initial run but passes on a retry.
5. Why use forbidOnly?
To prevent accidental focused tests from silently reducing the CI run to only a subset.
6. What is the difference between timeout and expect.timeout?
Test timeout controls the test's execution budget. expect.timeout controls how long an auto-retrying assertion waits.
7. What is globalTimeout?
A time limit for the complete test run, not one individual test.
8. What does test.slow() do?
It marks the test as slow and triples its test timeout. It does not intentionally slow execution.
9. Difference between skip, fixme and fail?
skip does not run a test; fixme marks it as needing a fix and does not run it; fail runs it and expects it to fail.
10. What is test.use()?
It overrides supported fixtures/options for a test file or describe group. It is not a mid-test browser reconfiguration API.
11. What is the difference between browserName and channel?
browserName selects the browser engine; channel selects a branded browser distribution such as Chrome or Edge.
12. What is storageState used for?
To load saved cookies and supported browser storage, commonly to reuse authentication state.
13. Does storageState save sessionStorage automatically?
No. Session storage requires separate handling.
14. What is the difference between a project and a worker?
A project is a named test configuration. A worker is an OS process that executes tests.
15. What is sharding?
Splitting the test suite into parts that can run in separate CI jobs or machines.
16. What is the difference between screenshot, video and trace?
Screenshot is a still image; video records visual execution; trace provides detailed debugging data such as actions, snapshots, network and timing.
17. Why are independent tests important?
They can run in any order and in parallel without relying on another test's state or data.
18. What is test.describe.configure({ mode: 'serial' })?
It runs tests in order and skips subsequent tests in that serial group after a failure. Serial mode is generally discouraged because it creates dependencies.
19. What does webServer do?
It starts a local application/server command and waits for the configured URL before tests run.
20. When would you use projects?
To run the same tests with different browsers, devices, environments or setup dependencies.
21. What happens when a test times out?
Playwright marks it as timed out. Investigate the operation, fixture, hook or assertion that consumed the available time.
22. Should you increase actionTimeout for every test?
Not automatically. First investigate locator quality, application response, synchronization and network conditions. A larger timeout can hide the real issue.
23. What is the difference between beforeAll and beforeEach?
beforeAll runs once per relevant worker/scope; beforeEach runs before each test. Do not assume beforeAll runs once across the whole CI pipeline.
24. Why might you use failOnFlakyTests?
To make CI reject flaky outcomes instead of treating a retry-passed test as acceptable.
25. What is retryStrategy?
A newer option controlling when failed tests are retried: immediate or isolated. It is documented as introduced in v1.62, so verify the installed version.

13. Practical assignments

  1. Create five tests and practise unconditional and conditional test.skip().
  2. Use test.only(), then enable forbidOnly and confirm the protection.
  3. Use test.fail() with a deliberately incorrect expected result; observe the outcome.
  4. Use test.fixme() and compare it with skip.
  5. Use test.slow() and test.setTimeout(); explain the difference.
  6. Group Account tests with test.describe() and add test.step().
  7. Use test.use() to set a different locale or viewport for one group.
  8. Configure retries and deliberately create a temporary flaky test to observe passed/flaky/failed outcomes.
  9. Run with 1, 2 and 4 workers. Observe execution time and resource usage.
  10. Compare normal file execution with fullyParallel: true.
  11. Create Chromium, Firefox and WebKit projects.
  12. Configure screenshot, video and trace policies; inspect a trace in Trace Viewer.
  13. Add smoke/regression tags and filter with --grep and --grep-invert.
  14. Run a three-shard suite using three CI jobs or local commands.
  15. Configure webServer for a local test application.
  16. Prepare a CI configuration with retries, worker limits, reports and failure artifacts.
